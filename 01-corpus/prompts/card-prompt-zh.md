# 单篇论文三层提取模板

主题：**面向洪水风险管理的水库调度调整**（Reservoir operation adjustment for flood risk management）。

你的工作角色是**水库调度与洪水风险管理研究专家**。请用该领域清楚、概括的功能语言整理论文，但所有具体判断、方法、参数和结论仍必须以论文文字为依据，不能用领域常识替代论文证据。

你将收到一份已经按页分隔的论文文字稿。请依据这份文字稿完成以下三层提取，在相关内容后标注页码或章节。论文没有报告的内容写“未报告”。

---

# 总体目标

本任务不是重新总结论文，也不是按照 Introduction–Methods–Results 的结构压缩论文内容。

你的目标是重建：

**作者面对什么问题 → 做出哪些判断 → 为什么做这些判断 → 如何把这些判断落实为研究或决策流程 → 用什么证据判断结果是否成立。**

最终结果应同时满足：

1. **忠实于单篇论文证据；**
2. **高于具体算法和模型一层进行功能性抽象；**
3. **清楚区分 reasoning 与 execution；**
4. **保留后续跨论文 pattern synthesis 和 micro-skill 提取所需的信息。**

---

# 在生成最终答案前：先完成研究逻辑重建

不要看到论文中的一个模型、算法或章节，就直接把它转换成一个步骤。

在填写最终三层结果之前，先在内部完成以下分析。

## A. 识别真正的研究判断

先回答：

1. 作者真正面对的核心科学问题或决策问题是什么？
2. 作者认为已有做法为什么不足？
3. 作者必须识别哪些不确定性、目标冲突、约束、信息缺口或评价困难？
4. 在选择具体模型之前，作者实际上做出了哪些方法论层面的判断？
5. 一个判断为什么会推动下一个判断？
6. 哪些内容只是技术实现，而不是 reasoning？

暂时去掉论文中的具体模型名、算法名、软件名和参数，然后重新检查作者的逻辑。

**如果删除这些技术名称后，一个所谓的 reasoning step 就失去了清楚的含义，则说明该步骤仍然过于 method-centric，需要继续向上抽象。**

---

## B. 区分三个分析层次

分析论文时严格区分：

### Level 1. Scientific reasoning

回答：

> 为什么这个问题必须被考虑或处理？

例如：

* 某种不确定性会改变决策；
* 两个安全目标之间存在冲突；
* 当前信息不足以支持唯一方案；
* 未来信息会更新，因此当前计划不能被视为固定行动。

### Level 2. Analytical strategy

回答：

> 基于上述判断，作者决定采用什么类型的处理逻辑？

例如：

* 保留多个权衡方案，而不是提前压缩成一个唯一最优方案；
* 显式表示不确定性，而不是使用单一确定性输入；
* 分离当前行动和未来可修正计划；
* 同时评价物理风险和方案排序的不确定性。

### Level 3. Technical implementation

回答：

> 论文具体用什么数据、模型、算法、公式、参数和软件实现？

例如：

* ensemble forecast；
* stochastic optimization；
* Monte Carlo simulation；
* TOPSIS；
* 某个具体求解器。

**Reasoning 部分主要表达 Level 1–2。**

**Execution 部分主要表达 Level 2–3。**

不要用 Level 3 的技术名称替代 Level 1–2 的研究判断。

---

# 1. 研究内容

用简洁语言回答以下三个问题：

| 要素      | 内容                                 |
| ------- | ---------------------------------- |
| 研究对象与问题 | 研究什么水库或系统？真正要解决什么调度或决策问题？          |
| 方法概述    | 用什么主要研究路线解决问题？只概括方法体系及其功能，不展开算法步骤。 |
| 研究意义    | 这项研究如何帮助理解或改进洪水风险管理下的水库调度？         |

研究内容只需要帮助读者快速理解这篇论文。

不要在这一层堆积具体模型名称、参数和实验结果。

---

# 2. 作者如何推理

## 2.1 推理层回答什么

Reasoning 回答：

> **作者为什么这样考虑、判断或选择？**

它不是 Methods section 的重新命名，也不是算法流程。

优先识别以下类型的功能性判断：

* 界定真正需要解决的决策问题；
* 诊断已有处理为什么不足；
* 判断哪些不确定性会影响后续决策；
* 澄清互相冲突的目标；
* 判断哪些约束或信息是决策相关的；
* 判断是否需要保留多个候选方案；
* 判断如何使用风险和偏好信息；
* 区分当前行动与未来可修正计划；
* 判断需要什么证据才能评价方案；
* 限定结论的适用范围。

不要直接把以下内容写成 reasoning step：

* 使用某个模型；
* 建立某个数学规划；
* 采用某个算法；
* 运行 Monte Carlo；
* 计算某个风险指标；
* 使用某个求解器；
* 做某个统计检验。

这些通常属于 execution，或者只是某个 reasoning step 的具体实现。

---

## 2.2 Reasoning step 自检

对每一个候选 reasoning step，内部检查：

> **如果删除其中所有模型名、算法名、参数和软件名，这一步是否仍然表达一个完整、可理解的科学判断或决策逻辑？**

如果不能，重新抽象。

再检查：

> **如果另一篇论文使用完全不同的算法解决同类问题，这个步骤名称是否仍然可能成立？**

如果不能，说明步骤名称可能仍然过于 paper-specific。

---

## 2.3 建立因果依赖关系

先用一段连贯文字重建作者的推理路线，再用表格展开。

不能只是：

A → B → C → D

而必须能够解释：

> 因为 A 发现了什么，所以作者下一步必须判断 B；
> 因为 B 又带来了什么问题，所以进一步需要 C。

对每两个连续步骤 Ri 和 Ri+1，内部检查是否能够形成以下句子：

> **Because [Ri 得出的认识或判断], the authors next needed to determine [Ri+1 的问题].**

如果无法自然建立这种关系：

* 合并步骤；
* 调整顺序；
* 或明确说明它们是并行分支。

不要按照论文的章节顺序机械排列步骤。

---

## 2.4 推理路线输出

推理路线叙述：

[用一段话连接 R1、R2……，说明作者先面对什么问题，为什么已有做法不足，因此识别出什么关键不确定性、目标冲突或信息需求，再据此形成什么处理逻辑，最后决定需要什么证据评价结果。]

随后填写：

| 步骤            | 作者为什么这样判断或选择              | 推理活动细节                                                                                     | 证据与边界                              |
| ------------- | ------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------- |
| R1. [功能性判断名称] | [作者面对什么判断问题；为什么必须作出这一判断。] | **触发条件：**[什么情况使这个判断成为必要。] **输入：**[需要哪些信息。] **判断依据：**[作者如何比较、权衡或决定。] **输出：**[该判断为后续工作提供什么。] | [页码和章节；明确作者直接表述与提取者重建；记录假设和未报告内容。] |

根据论文内容增加、合并或删除步骤。

每一步只表达一个主要推理功能。

---

# 3. 作者如何执行

## 3.1 执行层回答什么

Execution 回答：

> **作者具体怎样把上述判断落实为研究、分析或运行过程？**

Execution 不按照论文 Methods 中有几个模型来划分，而主要按照：

> **信息流、依赖关系和中间产物**

来拆解。

一个独立 execution step 通常应满足：

1. 有明确输入；
2. 完成一个主要操作；
3. 产生新的中间结果；
4. 这个结果被后续步骤使用，或者形成一个明确评价分支。

例如：

原始信息
→ 不确定性表示
→ 候选方案
→ 风险或性能指标
→ 方案评价
→ 当前行动
→ 信息更新
→ 下一轮决策。

---

## 3.2 不要过度拆分技术细节

以下内容通常不应单独成为 execution step：

* 一次矩阵分解；
* 一条公式计算；
* 软件调用；
* 求解器设置；
* 一个普通数据变换；
* 某个参数值；
* 一个中间数学操作。

除非这个技术操作会改变研究路线、产生独立中间产物，或者决定结果如何解释。

具体技术细节写在“执行活动细节”中。

---

## 3.3 区分主流程与评价分支

明确区分：

### 主研究/运行流程

真正产生最终方案、决策或研究结果的步骤。

### 评价分支

例如：

* baseline comparison；
* sensitivity analysis；
* robustness check；
* statistical test；
* scenario experiment；
* result interpretation。

不要为了让流程看起来连续，把这些评价活动硬塞进主执行链。

---

## 3.4 执行路线输出

先写一段连贯的执行路线：

[用一段话连接 E1、E2……，说明每一步接受什么输入，产生什么中间结果，以及下一步如何使用；明确循环、分支和只用于评价的步骤。]

随后填写：

| 步骤            | 作者具体做什么                   | 执行活动细节                                                                         | 检查、条件与证据                 |
| ------------- | ------------------------- | ------------------------------------------------------------------------------ | ------------------------ |
| E1. [功能性活动名称] | [作者完成什么具体工作，以及为什么需要这项工作。] | **输入：**[数据、前一步结果或设定。] **操作：**[实际处理过程、具体模型、算法、参数或分支。] **输出：**[产生什么，以及供后续哪一步使用。] | [如何检查；适用条件、假设、限制；页码和章节。] |

---

# 4. Functional abstraction 与 paper-specific realization

对于每一个重要的 Reasoning 和 Execution step，在内部先形成两个版本：

### Functional abstraction

> 这一步解决的一般研究、分析或决策功能是什么？

### Paper-specific realization

> 本篇论文具体使用什么方法实现？

最终的步骤名称优先使用 **Functional abstraction**。

论文的算法、模型、参数和软件写在详细说明中。

例如：

不推荐：

> 使用 MMFE 生成洪水预报

更推荐：

> 表示会随信息更新而变化的预报不确定性

具体细节再写：

> 本文使用 MMFE、方差—协方差矩阵和 Monte Carlo simulation 实现。

---

# 5. Evidence and inference audit

生成初稿后，必须进行一次证据和过度推断检查。

重点检查以下错误：

### 5.1 Proxy ≠ real-world consequence

例如：

* 水位超限概率不自动等于大坝失事概率；
* 泄流阈值超限不自动等于实际经济损失；
* 某个模型风险指标不能直接解释成人员风险。

### 5.2 Model result ≠ real-world performance

模拟案例、优化结果或模型比较不能自动解释为实际运行效果。

### 5.3 Sensitivity analysis ≠ independent validation

改变参数并观察结果稳定性，不等于独立数据或实际运行验证。

### 5.4 Ranking stability ≠ objectively better decision

排序更稳定、排名不确定性更低，不自动意味着实际决策更正确。

### 5.5 Case result ≠ general rule

单一案例得到的结果不能直接写成普遍规律。

### 5.6 Assumed parameter ≠ empirically calibrated parameter

实验设定、专家设定或主观参数不能描述为实测或校准结果。

### 5.7 Simulation ≠ deployment

数值案例、历史回放或情景实验不能描述为真实部署。

如果论文没有提供足够证据，应降低表述强度，并在“证据与边界”中明确说明。

---

# 6. 提取要求

* 推理层回答“为什么这样考虑或选择”；执行层回答“具体怎样完成”。
* Reasoning 重点保留 scientific reasoning 和 analytical strategy。
* Execution 重点保留 analytical strategy 和 technical implementation。
* 步骤名称必须使用功能性表达，而不是具体模型名称。
* 在推理和执行两层保留可用于后续 micro-skills 的：

  * trigger；
  * input；
  * judgment/action；
  * branch；
  * output；
  * check；
  * boundary。
* 区分研究动机中的 baseline 与实际实验比较的 baseline。
* 区分模型风险指标与真实后果。
* 区分 sensitivity analysis、robustness check 和 independent validation。
* 区分作者直接陈述与提取者根据论文结构重建的逻辑。
* 使用文字稿中的页码、章节、图表或公式作为证据位置。
* 论文没有报告的内容写“未报告”，不要用领域常识补写。
* 这是单篇论文提取，不进行跨文章 pattern synthesis，也不直接构建最终技能。
* 不要追求步骤越多越好。优先保证每一步具有独立功能和清楚依赖关系。
* Reasoning 和 Execution 的第一段路线叙述是主要阅读内容；表格用于支持和展开，不应取代路线叙述。

---

# 7. 最终质量检查

在输出最终答案前，逐项检查以下问题。

### Reasoning

* 是否主要在回答“为什么”？
* 是否存在直接对应某个 Methods subsection 的 reasoning step？
* 如果存在，它是否实际上只是给一个算法换了名字？
* 删除模型名和算法名后，每一步是否仍然成立？
* 相邻步骤之间是否有明确的因果或决策依赖？
* 是否存在应合并的重复步骤？
* 是否遗漏了“为什么已有方法不足”“为什么需要这种处理逻辑”之类的重要判断？

### Execution

* 是否能够沿着输入和输出追踪完整的信息流？
* 每一个主要步骤是否产生后续需要的中间结果？
* 是否把普通公式、求解器设置或软件操作误拆成独立步骤？
* 是否正确区分主流程与评价分支？
* 是否明确指出循环、更新或分支？

### Evidence

* 是否出现论文未支持的因果推断？
* 是否把模型指标解释成真实后果？
* 是否把敏感性分析解释成验证？
* 是否把案例结果写成一般规律？
* 是否把作者假设描述成实证事实？
* 是否清楚标记未报告内容？

### Reusability

最后再问一次：

> **如果下一篇论文使用不同的数据、模型和算法，但面对相似的水库调度问题，这套 Reasoning / Execution 步骤中有多少仍然有意义？**

如果大部分步骤只有在本篇具体算法存在时才成立，则说明抽象程度仍然不够，应重新检查。
