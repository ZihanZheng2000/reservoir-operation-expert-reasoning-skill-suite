# Real-Time Release Decision Tool for Large Flood-Control Reservoir

## Executive Summary

For a real-time release decision tool with a 30-minute computational budget, high forecast uncertainty, and ungauged tributary complications, I recommend a **simplified reservoir-river cascade model paired with scenario-based convex model predictive control (MPC), updated every 6 hours with rolling recourse**. The method balances forecast value against practical implementability and computational speed, using an ensemble-risk tolerance framework rather than optimal dispatch.

---

## 1. System Representation

### 1.1 Reservoir and Channel Model Structure

**Representation choices:**

- **Reservoir:** Single water-balance simulator with piecewise-linear level–storage and level–discharge-capacity relationships. 6-hour time steps (matching forecast update interval). Mass balance: S(t+1) = S(t) + I(t)·Δt − R(t)·Δt, where S is storage, I is inflow, R is release.

- **Downstream routing:** Integrator-delay model (not full dynamic hydraulics like SOBEK), calibrated against the 20-year hindcasts. Rationale: integrator-delay sits inside repeated optimization, is 10–100× faster than dynamic models, and achieves NSE ≈ 0.97 on similar systems (reference E23-R4). The channel reach (120 km, multiple tributary entries) is represented as a sequence of storage elements with first-order response.

- **Ungauged tributaries:** Distribute their contribution as a time-varying but uncertain inflow at the control station. Treat as a scenario-dependent perturbation rather than a separate model:
  - Use the 20-year hindcast observations to estimate tributary contribution statistics (lumped at the control station, time-dependent correlation with dam releases).
  - In each scenario, draw tributary flow as a proportional perturbation on the main-stem forecast (e.g., tributary flow ~ N(μ_trib, σ_trib) with lead-time-dependent σ).
  - Do not model tributaries as a separate routing chain; instead, route the dam release through the main channel and add tributary uncertainty to the downstream level/flow prediction.

**Why this structure:**
- The 30-minute budget rules out full-physics models but allows 6-hour-step simplified routing inside MPC.
- Scenario-based treatment of tributaries avoids needing real-time tributary forecasts (which are unavailable) while preserving ensemble dependence.
- Piecewise-linear curves avoid expensive nonlinear optimization and allow convex formulations.

### 1.2 Forecast Integration

- **Ensemble inflow forecasts:** Use the 51-member ensemble at 6-hour intervals. Each member generates a 10-day sequence.
- **Forecast error:** Quantify from 20-year hindcasts. Lead-time-dependent error structure: σ(t) increases with lead time; test for non-normality and heteroscedasticity by inflow magnitude. Likely structure: small forecasts (< 5,000 m³/s) have larger relative error; large forecasts (> 10,000 m³/s) have smaller relative error but greater absolute error.
- **Scenario tree construction:** Do not use all 51 members; reduce to 10–16 representative branches using a scenario-reduction algorithm (e.g., Kantorovich distance or k-means on cumulative inflow over the 10-day horizon). Rationale: keeps the tree size manageable for MPC (hundreds of variables and constraints, not thousands) while preserving ensemble dependence structure.

## 2. Modeling and Solution Method

### 2.1 Model Formulation

**Objective:** Minimize expected peak downstream level and peak release under a risk tolerance constraint.

**Deterministic equivalent (multi-stage stochastic program):**

Over a 10-day rolling horizon with 6-hour steps (40 periods):

```
Minimize:  E_ω[ α·max_t Z_downstream(t,ω) + (1−α)·max_t R(t,ω) ]

Subject to:
  - Mass balance (per member/scenario)
  - Release bounds: 0 ≤ R(t) ≤ R_max(Z(t))  [discharge capacity curve]
  - Release ramping: |R(t) − R(t−1)| ≤ Ramp_max
  - Storage bounds: S_min ≤ S(t) ≤ S_max
  - Downstream level constraint (chance): P(Z_downstream > Z_safe) ≤ P_acceptable
  - Non-anticipativity: R(t) same across all scenarios ω (non-anticipative current decision)
```

**Non-anticipativity:** At each 6-hour recomputation, impose that the current release R(t) is the same for all ensemble members, but future releases R(t+1), R(t+2), ... can depend on the scenario branch (tree structure). Rationale: operators cannot implement different releases simultaneously; they commit to the next 6 hours, then update when the forecast refreshes.

### 2.2 Why This Method, Not Alternatives

**Alternative 1: Dynamic stochastic programming (SDP)**
- Pro: Theoretically optimal, handles nonlinearity.
- Con: Curse of dimensionality for 51 ensemble members and continuous storage state. Typical SDP has 10–20 state bins; loses information.
- Chosen against: No SDP instances in the literature solve 51-member flood-control problems in 30 min.

**Alternative 2: Monte Carlo search (enumeration)**
- Pro: Model-free, robust to forecast errors.
- Con: With 51 members × 40 steps, even sampling 1,000 candidate release sequences would require 1,000 × 40 = 40,000 model runs. At 30 sec per run, exceeds 30 min.
- Chosen against: Too slow unless the search is drastically reduced (e.g., 100 sequences), losing decision reliability.

**Alternative 3: Deterministic optimization (perfect forecast)**
- Pro: Fast; produces a benchmark.
- Con: Ignores ensemble uncertainty. In real floods, ignoring uncertainty leads to either insufficient pre-release (overtopping risk) or excessive pre-release (water waste). Not acceptable for operators.
- Chosen as a reference, not primary method.

**Why scenario-based convex MPC:**
- The 51-member ensemble is already available and updated every 6 hours; using it directly (via a tree) is natural.
- Convex formulation (piecewise-linear curves, quadratic objectives, linear constraints) solves in seconds to minutes, not hours.
- Rolling implementation (solve once, execute one step, recompute with new forecast) adapts to real-time forecast updates and observed inflow changes.
- Literature precedent: E17-R2 chose scenario-based convex MPC over SDP for the same reason (scalability).

### 2.3 Solver and Implementation

- **Solver:** CVXPY with SCS (splitting conic solver) or Clarabel. Open-source, handles convex QPs in seconds for problem sizes up to ~5,000 variables and ~10,000 constraints.
- **Tree size:** 12–16 representative members, 40 time steps, 2 decision stages (today's release, future releases per branch) → ~480–960 variables, ~1,000–2,000 constraints. Expected solve time: 5–15 seconds.
- **Computational safeguard:** If solver timeout is triggered (>25 min), fall back to a measurement-based rule: release = f(current_level, observed_inflow) to guarantee sub-30-min decisions.

## 3. Adaptive Logic and Flood Stages

The tool does not switch between fundamentally different rules; instead, it re-solves MPC each 6 hours as:
- Forecast updates,
- Reservoir level and inflow change,
- Risk tolerance evolves during the event.

**Flood stage representation within MPC:**
- Pre-release stage: objective α favors storage (avoid spill); risk tolerance is tight to maximize pre-event drawdown.
- Peak-control stage: α shifts toward peak-release minimization; downstream level constraint tightens.
- Recession stage: α shifts to refill; constraint relaxes.

**Implementation:** Encode stage transition as a time-dependent weighting function α(t) that evolves over the 10-day horizon. Example: α = 0.7 for days 1–3 (storage priority), 0.3 for day 4–7 (release priority), 0.5 for days 8–10 (refill).

## 4. Decision Output and Practical Implementability

**What the tool outputs every 6 hours:**

1. **Recommended release for the next 6 hours:** R(t), in m³/s. Operators implement this as a target gate opening or pump setting.
2. **Expected range of releases over the next 24 hours:** [R_min, R_max], conveying uncertainty and showing operators what adaptations may come.
3. **Confidence in the recommendation:** Percentage of ensemble members agreeing that the release keeps downstream level below Z_safe. If <70%, flag a decision as low-confidence.
4. **Trigger for fallback:** If the 10-day forecast changes by >20% inflow or observed inflow deviates >±25% from the ensemble mean, re-optimize immediately (not waiting for the 6-hour cycle).

**Explainability for regulators:**

- **Rationale:** "The ensemble forecast predicts X m³/s average inflow, current storage is Y%, and the downstream warning level is Z m. To keep downstream flood risk below [acceptable level], we release R m³/s now and will adjust it in 6 hours when the forecast updates."
- **Uncertainty disclosure:** "10 of the 16 ensemble members predict the flood peak within a ±15% range; 3 members suggest a larger peak. Our release plan accommodates the 90th-percentile scenario."
- **Verifiability:** Show a chart (hindcast time series + ensemble envelope) so regulators can see whether past forecasts were reliable at this lead time.

## 5. Verification of Key Requirements

### 5.1 Computational Efficiency (30-minute goal)

**Verification plan:**

1. **Offline profiling:** Solve the optimization 100 times with random inflow/storage states. Record CPU time distribution (median, 95th percentile). Target: median < 10 sec, 95th percentile < 20 sec, leaving 10 min for data I/O, forecast processing, and contingency.

2. **On-hardware testing:** Run the tool on the target hardware (e.g., a standard server or cloud instance) with real data and actual ensemble members. Log solve time, solver convergence status, and memory use at each 6-hour step over a historical flood (e.g., 1-month event). Ensure 100% of runs complete in <25 min.

3. **Scalability check:** Test with 20, 12, and 8 ensemble branches. If solve time scales linearly (expected for convex MPC), document the time-vs-members trade-off so operators can adjust ensemble size if hardware constraints tighten in the future.

4. **Fallback trigger:** Log how often the measurement-based fallback is invoked (should be < 1% of 6-hour cycles). If fallback is >5%, the optimization needs tuning or hardware upgrade.

### 5.2 Physical Constraints (levels, discharge capacity, ramping, refill)

**Verification plan:**

1. **Constraint satisfaction audit:** Run the tool over 20 years of hindcasts. For each 6-hour decision, check:
   - Does the recommended release exceed outlet capacity at the current level? (Should be 0 violations)
   - Does storage exceed S_max? (Should be 0)
   - Does release ramping exceed physical gate limits? (Should be 0)
   
   Report constraint violation rates (target: zero, accept <0.1% due to rounding).

2. **Refill adequacy:** After each flood event, check whether the tool allowed storage to recover to near-normal levels within 30 days. Benchmark against historical refill patterns. If refill is slower than historical, investigate whether the risk tolerance is too tight or whether the forecast is overly pessimistic.

3. **Level-capacity relationship verification:** Validate the piecewise-linear discharge-capacity curves against rating tables or SOBEK simulations at 10 representative levels. NSE or RMSE on stage-discharge should exceed 0.95.

### 5.3 Decision Reliability and Forecast Sensitivity

**Verification plan:**

1. **Hindcast reanalysis:** Replay the tool over 2–5 major historical floods (using real forecasts or synthetic ensemble hindcasts). Compare the tool's recommended releases with what actually happened:
   - Did the tool recommend sufficient pre-release when the actual flood was larger than the median forecast?
   - Did the tool avoid excessive pre-release when the actual flood was smaller?
   - Quantify both over-release (water wasted) and under-release (refill delay or overtopping) as percentage-of-event-volume metrics.

2. **Forecast error sensitivity:** Run MPC on the same historical floods but with artificially degraded forecasts (e.g., increase σ by 50%, add +10% bias, reduce ensemble spread). How much does the recommended release change? Acceptable result: the tool adjusts conservatively (prerelease more, not less) when forecast uncertainty rises.

3. **Robustness to trigger events:** Run the tool with:
   - Missing forecast (use climatology): tool should still produce a safe release (via fallback or conservative defaults).
   - Sudden inflow jump (e.g., a large tributary contribution not in forecast): tool should adapt within one 6-hour cycle.
   - Forecast bias detected mid-event (e.g., observed inflow 20% higher than ensemble mean): triggers immediate re-optimization.

### 5.4 Practical Implementability

**Verification plan:**

1. **Operator comprehension trial:** Engage 3–5 dam operators at the target reservoir. Present 10 historical release decisions (with dates removed) and ask them to explain the recommended release in their own words, then check their understanding against the tool's intent. Success: >80% of explanations align with the risk/forecast rationale.

2. **Gate actuator compatibility:** Confirm that the recommended release rates (e.g., 200–5,000 m³/s in increments of 100 m³/s) can be achieved by the spillway and outlet gates. If precision is insufficient, implement a rounding/discretization step in the tool output.

3. **Stakeholder review checklist:**
   - Is the forecast lead time sufficient to execute the recommended action? (Test by measuring the time from "forecast issued" to "release must change"; typically 4–6 hours. Lead time is 10 days, so yes.)
   - Can regulators verify the tool's rationale from accessible data (forecasts, storage, observed levels)? (Yes, if the tool logs decision inputs.)
   - What is the fallback if the tool fails? (Measurement-based rule: release as a function of current level and observed 24-h average inflow.)

## 6. Handling Uncertainties in Data and Constraints

### 6.1 Ungauged Tributary Flows

**Uncertainty:** The two ungauged tributaries enter during the 120 km reach; their real-time flows are unknown.

**Strategy:**
- **Observation:** 20 years of measured control-station flow includes both main-stem and tributary contributions. Decompose this into main-stem (from dam routing model) and tributary residual using data assimilation (e.g., Kalman filter on the residuals).
- **Regression model:** Fit tributary flow as a function of season and recent main-stem inflow. Example: Q_trib(t) ~ f(main_stem_inflow(t−6), season, rainfall). Use multivariate regression on the 20-year decomposed series.
- **Ensemble expansion:** For each of the 51 main-stem ensemble members, generate a tributary perturbation using the regression model + residual noise. Adds ~20% uncertainty to peak downstream flow, which is significant but not catastrophic.
- **Adaptive update:** If real-time observation becomes available (e.g., a rapid-response gage is installed mid-project), incorporate it via Kalman filter within MPC.

### 6.2 Discharge-Capacity Relationship under Extreme Levels

**Uncertainty:** The level–discharge relationship is calibrated on 20-year data; it may not extrapolate reliably to floods beyond the 95th-percentile level.

**Strategy:**
- **Stress test:** Use hydraulic engineering judgments (e.g., USBR methods) to bound the discharge-capacity curve at extreme levels. Example: if the normal curve gives Q_max(Z=highest_level) = 15,000 m³/s, a physics-based upper bound might be 16,000 m³/s (accounting for increased head) and a lower bound might be 14,500 m³/s (accounting for submergence losses).
- **Robust bounds:** Implement the MPC with the *lower bound* as the constraint (conservative), and perform sensitivity analysis with the upper bound. If decisions change significantly, recommend recalibration or field measurement of the relationship at high levels.
- **Fallback:** If actual discharge approaches these limits, the tool flags an alert: "Discharge approaching design capacity; additional margin required."

### 6.3 Forecast Skill Degradation Beyond Day 7

**Uncertainty:** HEFS ensemble skill decreases with lead time; beyond 7–10 days, forecasts become climatological.

**Strategy:**
- **Lead-time-dependent risk tolerance:** Define acceptable risk as a function of lead time. For t ≤ 7 days, P(over-FLWL) ≤ 1%; for t > 7 days, P(over-FLWL) ≤ 2% (more lenient, because forecast uncertainty dominates). This is encoded in the chance constraint.
- **Post-horizon design flood:** Beyond the forecast horizon (day 10), assume a design flood (e.g., 100-year event) enters at the control station. Route it assuming no-forecast release strategy (e.g., hold to FLWL). This bounds risk beyond day 10.
- **Verification:** Quantify HEFS skill (CRPS, rank histogram, bias) at lead times 1–10 days against 20-year hindcasts. If CRPS degrades sharply (e.g., doubles) after day 7, tighten the pre-release window to days 1–7 and make days 8–10 defensive (maintain extra storage margin).

### 6.4 Forecast Bias and Real-Time Correction

**Uncertainty:** Ensemble forecasts may have systematic bias (e.g., underforecast in summer monsoons).

**Strategy:**
- **Bias correction:** Fit a seasonal additive/multiplicative bias model to hindcasts (e.g., Q_forecast,corrected = Q_forecast + c_season(t)). Apply this pre-processing to each ensemble member.
- **Adaptive bias learning:** During operations, log observed_inflow − ensemble_mean at each 6-hour step. Fit a rolling bias estimate (e.g., 30-day window) and update the bias correction online.
- **Trigger for concern:** If observed inflow exceeds the 90th-percentile ensemble member by >30%, the tool flags a decision as "forecast skill low; increase safety margin" and can optionally trigger a manual override review.

### 6.5 Climate Nonstationarity and Long-Term Drift

**Uncertainty:** Flood regime may be changing (e.g., climate change, land-use change).

**Strategy:**
- **Periodic recalibration:** Every 2–3 years, refit the forecast-error model and tributary-flow regression using the most recent 5–10 years of data.
- **Trend detection:** Use a statistical test (e.g., Mann–Kendall) on annual peak inflows and annual forecast skill to detect whether the 20-year hindcast record is representative. If a significant trend is detected, document it and adjust forecast-error parameters accordingly.
- **Contingency:** If recalibration shows a major shift (e.g., ensemble RMSE increases by >50%), escalate to a review of the forecast model and consider retraining the ensemble on updated meteorology.

## 7. Development and Deployment Pathway

### Phase 1: Offline Setup (Months 1–3)
- Build the integrator-delay routing model; validate against SOBEK on the 20-year hindcasts.
- Construct the scenario tree reduction algorithm and test it on 10 historical floods.
- Implement the MPC formulation in CVXPY.
- Conduct the computational benchmarks (Sec. 5.1) to confirm <30-min runtime.

### Phase 2: Hindcast Reanalysis (Months 2–4)
- Replay the tool over 2–5 major floods; audit constraint satisfaction and decision reliability.
- Engage operators and regulators in reviewing hindcast decisions.
- Finalize the risk-tolerance parameters and stage-dependent weights.

### Phase 3: Pilot Implementation (Months 4–6)
- Operate the tool in parallel with the current manual operation for 1–2 flood seasons.
- Log all decisions (recommended releases, ensemble forecasts, observed flows).
- Compare tool recommendations with actual operations; refine uncertainty models if systematic discrepancies emerge.

### Phase 4: Transition to Operational Use (Month 6+)
- Switch tool to primary decision support; retain human override capability.
- Establish a post-event review protocol: after each flood, audit tool performance and update forecast-bias models.

## 8. Summary of Key Assumptions and Known Limitations

1. **Ensemble sufficiency:** Assumes the 51-member HEFS ensemble captures forecast uncertainty adequately. If ensemble spread is systematically too narrow or biased, decisions could be unduly risky.

2. **Ungauged tributaries:** Treated as a lumped perturbation at the control station, not routed individually. If tributaries have different travel times or are substantially larger, a more detailed cascade model may be needed.

3. **Simplified routing:** Integrator-delay is fast but cannot capture backwater effects or time-varying channel storage precisely. If the 120 km reach has significant length or complex geometry, validate integrator-delay against SOBEK; if NSE < 0.90, use a higher-fidelity model at the cost of longer computation.

4. **Convex MPC:** Formulation assumes piecewise-linear level–discharge and level–storage relationships. Highly nonlinear behavior (e.g., vortex formation, gate cavitation) is not explicitly represented; safeguards via constraint bounds are needed.

5. **Operator acceptance:** Tool output must be explainable and verifiable. If operators distrust ensemble forecasts or find the recommendations counterintuitive, adoption will fail. Engagement and training are essential.
