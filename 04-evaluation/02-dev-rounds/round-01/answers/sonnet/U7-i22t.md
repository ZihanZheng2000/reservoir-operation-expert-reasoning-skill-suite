# Real-time flood release tool: representation, method, verification

## 1. Provisional recommendation

Use a **receding-horizon, scenario-based stochastic optimisation (multi-stage MPC) with CVaR or chance-constrained risk terms**. Wrap it in a **rule-based guard-rail layer**, a **full-fidelity simulation check**, and an **explanation layer**.

- The core is a linear or mixed-integer-linear program over the 10-day horizon.
- It uses the ensemble members (or a tail-preserving reduction of them) as scenarios.
- Only the first 6-12 h of the plan are committed. The problem is re-solved every 6 h when a new forecast arrives.
- The output is the release schedule operators carry out, plus a short justification.

What would change this recommendation:

- Solve times that cannot meet the 30-minute budget with all members. The fallback is scenario reduction, then a coarser time grid.
- Operating rules that cannot be expressed as linear or piecewise-linear constraints.
- A hindcast showing the ensemble is so badly calibrated that scenario weights are meaningless. In that case the first fix is post-processing, not a different optimiser.

## 2. System representation

**Time grid.**
- Use a variable grid, for example 1-3 h steps for the first 48 h and 6 h steps out to day 10.
- Finer steps early capture gate actions and the flood wave arriving at the control station.
- Coarser steps late keep the model small.

**Reservoir state.**
- The state is storage S_t. Level h(S) comes from the level-storage curve. Mass balance is S_{t+1} = S_t + (I_t - R_t - losses)·Δt.
- The decision is the release R_t, the total discharge through gates and spillway.

**Discharge capacity.**
- Capacity Qcap(h) varies strongly with level, so it must be in the model. The plan must not assume a release the structure cannot pass at the level it will actually have.
- This makes early pre-release the key decision. It is also what makes the problem non-convex if Qcap is convex in S, as with weir-type spillways.
- Handling:
  - Use a conservative piecewise-linear bound on Qcap(S), taking the lower of the start-of-step and end-of-step capacity.
  - Tighten it with a few sequential-LP or trust-region iterations around the previous solution.
  - Use SOS2 or binaries only if the curve has real gate-regime breakpoints.
- Any approximation error is checked afterwards in the simulator (section 4).

**Operational constraints** (placeholders until confirmed, see section 5):
- Minimum release.
- Release ramp limits, up and down.
- Discrete or staged gate openings and minimum hold times.
- Maximum allowable downstream flow or stage.
- Flood-limit level and the level to restore at the end of the event.
- Surcharge or dam-safety level.

**Channel (120 km).**
- The calibrated routing model is probably nonlinear (Muskingum-Cunge or hydrodynamic) and too slow to put inside the optimiser.
- Build a **surrogate** from it: a time-varying lag-and-attenuate or impulse-response form, with parameters fitted over the range of flows seen and over synthetic flood ramps.
- Quantify surrogate error against the full model, especially at high flows and for rapidly changing releases, where nonlinearity matters.
- Use the full model only as a **check and correction step** on the final candidate schedule (section 4).
- Release at t reaches the control station at t + τ. This lag couples the decision to the downstream constraint, so the optimiser sees downstream flow as Q_ctrl(t) = routed(R) + tributary contributions.

**Ungauged tributaries.**
- Treat them as an uncertain additive lateral inflow, not as known data.
- Estimate their history by residual: observed control-station flow minus the routed dam outflow. This gives a 20-year lumped tributary series, assuming the reach is otherwise closed.
- Fit an error and uncertainty model to that series. Condition it on the same rainfall events as the ensemble, since tributaries and the dam inflow respond to the same storms. Use rainfall-runoff or regionalisation only if meteorological forcing is available, which is not stated.
- In real time, update the lateral flow estimate from the latest residual (data assimilation or a persistence-with-decay term).
- Carry the uncertainty into the optimiser as:
  - extra scenarios or additive scenario offsets, **or**
  - a safety margin on the control-station constraint, sized by the hindcast residual distribution.

**Scenarios.**
- 51 members × tributary uncertainty. Try all 51 first.
- If solve time requires it, reduce to about 8-15 scenarios by clustering on flood volume, peak and timing, always keeping the tail members and weighting by probability.
- Non-anticipativity: the first-stage decisions (next 6-12 h) are common to all scenarios. Later decisions may differ by scenario (recourse).

**Objective.**
Lexicographic or tiered, with slack variables:
1. Dam safety: hard in all scenarios, or at a very high chance level.
2. Downstream flood threshold at the control station: chance-constrained or CVaR-penalised.
3. Operability: minimise release changes and gate moves.
4. Restore flood-control storage by the end of the horizon.
5. Preserve beneficial use or conservation, last.

## 3. Why this method, and not the alternatives

| Alternative | Why not the primary choice |
|---|---|
| **Fixed rule curves or current operating rules alone** | Most explainable, but they ignore the 10-day ensemble. They cannot do forecast-based pre-release. Kept as the **baseline and guard rail**. |
| **Deterministic MPC on the ensemble mean** | Cheap and simple, but it hides tail risk. Flood decisions are driven by the upper members and by timing spread. Used as a comparison baseline. |
| **Stochastic DP / SDDP** | Handles uncertainty in principle, but needs a Markov inflow model that loses the ensemble's information. The state-space grows with the channel and tributary representation. The policy is hard to explain to a regulator. Poor fit for a 6-hourly forecast-driven problem. |
| **Metaheuristics (GA, PSO)** | Flexible, but no optimality or feasibility guarantee, variable runtime, and the answers are hard to explain. |
| **Reinforcement learning or learned policy** | Explainability and hard-constraint guarantees are weak. Rare extreme floods are underrepresented in 20 years. Could be useful later as a warm-start or advisory comparison, not as the decision engine. |
| **Full nonlinear MPC with the full routing model inside** | Fidelity is high but the 30-minute limit and solver robustness are at risk. Use the full model for checking, not inside the loop. |

Why the chosen method fits:
- LP/MILP solvers are fast and deterministic, with certificates of optimality or infeasibility.
- Constraints are explicit, and their duals and binding status can be reported.
- It uses the whole ensemble and updates as forecasts change.
- A large LP (51 scenarios × about 100 steps) is expected to solve in seconds to minutes. This needs to be confirmed on the actual hardware.

## 4. Verification plan

### 4.1 Computational efficiency
- Time the full cycle: data ingest, scenario build, solve, full-model check, report. Run it across all 6-hourly cycles of the 20-year hindcast, cold start and warm start.
- Report the median, 95th and 99th percentile, and the worst case. The worst case is the largest flood, with the most binding constraints.
- Acceptance target: the 99th percentile well under 30 min, with margin for slower hardware. Provisionally, the solver should use no more than about one third of the budget.
- Design in an anytime fallback. A time-limited solve returns the best feasible incumbent. If there is none, a precomputed rule-based release is used and flagged as such.

### 4.2 Physical constraints
- Mass balance must close in the optimiser and in the simulator.
- Replay each recommended schedule through a **fine-step simulator** using the true level-storage curve, the true Qcap(h), and the full routing model. Check:
  - No release exceeds the capacity at the simulated level. This is where the piecewise-linear approximation and the start-of-step convention are tested.
  - Level stays within bounds. Release rates and ramps are respected.
  - Downstream flow computed by the surrogate and by the full model agree within a stated tolerance. If not, correct the surrogate or add a margin and re-solve.
- Run sensitivity on the rating curve, including any hysteresis or gate-regime effects, once those are known.

### 4.3 Decision reliability
**Forecast quality first.**
- Check ensemble reliability on the 20-year hindcast: rank histograms, CRPS, reliability of exceedance of flood thresholds, and bias and spread by lead time and flood size.
- If the ensemble is under-dispersive, apply post-processing before using it as scenarios.

**Closed-loop hindcast.**
- For every flood event, replay each 6 h cycle with the forecast issued then. Simulate the consequences with the observed inflow and tributary flow.
- Metrics:
  - peak level and dam-safety exceedances;
  - downstream threshold exceedance, duration and magnitude;
  - release variability and number of gate moves;
  - end-of-event storage recovery.
- Compare against: historical operator releases, the current rule, deterministic MPC on the ensemble mean, and perfect-foresight as an upper bound.
- Evaluate with leave-one-event-out or leave-one-year-out cross-validation. This applies to any tuned parameter such as risk level, safety margin, or tributary error model.
- Calibrate risk parameters so the **empirical** violation rate matches the nominal one. Report confidence intervals, for example by bootstrapping events. Twenty years contains few extreme events, so state this limitation explicitly.

**Stress tests.**
- Scaled and time-shifted floods, including inflows larger than anything in the hindcast.
- Forecast failure: missing, stale or biased forecasts, and a missed peak.
- Tributary flows at the upper end of the residual distribution.
- Gate unavailable.
- Check that the tool degrades safely to guard-rail rules.

### 4.4 Practical implementability and explainability
- **Operator review.** Run a tabletop exercise on historic and synthetic events and ask operators to judge whether each recommendation is feasible and understandable.
- **Shadow mode.** Run the tool in parallel with real operations for at least one flood season or equivalent before it is relied on. Log the tool's output, what operators did, and the outcome.
- **Guard rails.** Hard-code the regulator-approved rules as constraints. If the optimiser output falls outside the permitted envelope, it is rejected and the rule-based release is used.
- **Output for each decision**:
  - the recommended release, tied to implementable gate steps;
  - which constraint is binding and why (e.g. "pre-release is needed because in N of 51 members the level would exceed X");
  - the trade-off cost of safer and less-safe alternatives;
  - a comparison with the rule-based release;
  - a counterfactual: what happens under the worst member and under the median.
- Operators may override. The tool should re-solve with the override fixed and show the consequence.
- **Auditability.** Store inputs, scenario set, parameters, solver status and outputs for each cycle so every recommendation can be reproduced for the regulator.

## 5. Handling unclear data and constraints in the preliminary design

I would not invent these values. I would treat each as an explicit **assumption with an owner, a default and a revisit trigger**, held in a configuration file so changes do not require code changes.

| Unknown | Preliminary handling |
|---|---|
| Regulator rules (flood-limit level, surcharge level, max downstream stage, ramp limits) | Placeholder values from the existing operating manual if available; request the formal rules before shadow mode. Make them configurable constraints. |
| Gate operation detail (discrete openings, hold times, outages) | Start with continuous releases plus a ramp limit and a post-processing step that maps to feasible gate settings. Later add MILP gate logic if needed. |
| Objective weights and acceptable risk level | Use a lexicographic order (safety, then downstream, then smoothness) and present the trade-off curve. Ask the owner to choose the risk level. |
| Tributary forecasts and their uncertainty | Use the residual-based model above, with a conservative margin. Test sensitivity. Improve if rainfall data become available. |
| Whether the ensemble reflects upstream operations or is biased | Check on the hindcast. Post-process if needed. |
| Real-time data latency, quality and observation error (including how inflow is estimated) | Add data-quality checks and a stale-data fallback. Include inflow estimation error in the scenarios. |
| Rating curve uncertainty or hysteresis | Use conservative capacity. Test sensitivity. |
| Hardware and solver licensing | Prefer an open or widely available solver. Benchmark on target hardware. |

Principles:
- Where a missing item could make the tool unsafe, use the conservative option and report it.
- Where it affects only comfort or efficiency, use a simple default.
- Run a sensitivity study on every assumption, and rank which ones most change the recommendation. Resolve those first.
- Stage the build:
  1. an offline hindcast prototype with a simple surrogate;
  2. the fine-step simulator check;
  3. operator tabletop exercises;
  4. shadow mode;
  5. advisory use under regulator review.
- Each stage has pass/fail criteria agreed in advance.
